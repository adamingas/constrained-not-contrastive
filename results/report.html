CLM versus a single constrained output token

The proposed A/B/C/D/E baseline is valid. In this experiment, with a reusable options-prefix KV cache, it was within 11% of CLM's median latency across four workloads. The evidence inspected does not establish a 9× advantage over this baseline.

Apple M4 Max · 64 GB · original BF16 Qwen3-8B · MLX · released CLM checkpoint. Exploratory measurements, not a general accuracy leaderboard or a reproduction of NVIDIA/vLLM timings.

What was actually compared

Both paths use the same frozen Qwen3-8B transformer weights. CLM processes plain state-plus-question text, takes the final-token representation, normalizes it, and applies the released state head. Each action description is separately encoded and projected by the action head. Candidate vectors are cached, then scored using scaled cosine similarity.

The constrained baseline places the option definitions in the system message, puts the state and question afterward, disables thinking with enable_thinking=False, and reads the logits for single-token option letters at the end of that one prompt forward pass. It never feeds the selected letter back through the transformer. A further optimized version computes only the corresponding rows of the LM output matrix. The full-vocabulary version computes the last-position output projection normally, then selects the allowed labels.

CLM:
  z_state = normalize(state_head(normalize(Qwen(state + question)[last])))
  z_action[i] = normalize(action_head(normalize(Qwen(action[i])[last])))
  score[i] = scale * dot(z_state, z_action[i])

Constrained Qwen:
  h = Qwen(options + state + question + answer_prefix)[last]
  score[i] = dot(lm_head.weight[token_id(label[i])], h)

Both:
  probabilities = softmax(scores over allowed options)
  choice = argmax(scores)

The output weight for “A” is not an embedding of “jump right.” Its meaning comes from the prompt, which contextualizes the final hidden state. In this Qwen checkpoint, input embeddings and LM output weights are not tied. The semantic comparison is implemented through the transformer's joint processing of the options and state.

These 35 questions were authored for this investigation before running the models. They cover customer routing, textual Mario situations, and numerical comparisons. They are too small and informal to establish broad superiority. The two systems also have different training objectives and data; this is an off-the-shelf comparison, not a controlled training ablation.

Both models classify the user's duplicate-invoice example as billing. The local CLM distribution is approximately 98.8% billing and 1.2% technical. This need not exactly equal the illustrative README probabilities. Some CLM errors favor “jump left” across quite different Mario states. Qwen also makes mistakes, and reversing option order changes 3/10 Mario answers and all 5 numerical answers. Constraining the format guarantees a valid option, not correctness or calibration. Neither method's softmax should automatically be interpreted as a calibrated probability of success.

T-Rex: what the original demo measures

The published T-Rex harness computes action safety with an exact-physics planner, includes “Safe,” “Unsafe,” and “Best” in the candidate descriptions, and enables a shield that can replace unsafe answers or intervene at execution time. Thus it is a planner-assisted selector benchmark. Survival is a property of the combined model, planner, scheduling and shield.

The committed reports give CLM 5/5 surviving courses, 65.8% planner agreement and 4,883 combined shield interventions; Jev also survives 5/5, with 98.7% agreement and 28 interventions. Their median client-side request latencies are 16.5 ms and 149.8 ms. CLM is served locally on an RTX 4090 while Jev is accessed through its hosted API. These observations can support a deployment-level speed comparison, but they do not isolate architecture or compare against local constrained Qwen. Sources: CLM results, Jev results.

Both methods receive the upstream planner's labeled candidate descriptions. The same deterministic engine runs two seeds for up to 20 simulated seconds, with one choice every six frames. No safety shield or emergency override changes the answer. A planner-only control survives both courses. Game time pauses during inference, and identical full requests are memoized for both models; these game runs are not a latency benchmark. Reported crash times are rounded to the six-frame decision interval.

Constrained Qwen follows the planner's best action on all 400 decisions and survives both courses. CLM crashes in both. This shows that the proposed constrained decoder can perform the supplied demo's selection task well on these courses; it does not establish unaided game intelligence or real-time survival at these local inference latencies. The Mario test above uses textual situations only; an actual Mario emulator was not run.

What is genuinely different about CLM?

  • Different supervision. CLM's heads are trained to align state–action pairs and reject alternatives through a contrastive objective. Qwen's output head was trained to predict text. A relatively small nonlinear head can substantially change a ranking by learning which backbone features matter. Small parameter count does not imply no useful learning.
  • Independent candidate reuse. CLM can encode an action once and reuse it across states, candidate reorderings and different subsets. A causal options-prefix cache is tied to the exact token prefix and its order. Each new state token still attends to that cached prefix; CLM's state transformer does not attend to the candidate texts.
  • Compact candidate storage. The released head emits 512-dimensional vectors: approximately 2 KiB per projected FP32 action. Qwen3-8B's ordinary BF16 KV cache costs about 144 KiB per cached token, before allocation overhead (36 layers × K/V × 8 KV heads × 128 dimensions × 2 bytes). Memory, large candidate sets and repeated candidate subsets can matter even when small-set latency is close.
  • A representational tradeoff. In the independent-input form, a CLM action's raw score cannot change when another candidate is added; only its normalized probability changes. Joint prompting can reason about relations among alternatives. For example, identifying the middle-priced item requires knowing which other items are offered. Putting the options into CLM's state can expose that information, but changes the independent-state caching advantage.
  • Cheap head training. The frozen backbone permits precomputing embeddings and training only small heads. This is a real training and adaptation benefit, separate from whether one-token inference is faster.

The released checkpoint contains 18,887,680 total head parameters, split equally between state and action heads. Its approximately 75 MB file stores FP32 weights; it is not a 75-million-parameter MLP. Its actual topology is 4096 → 1536 → 1536 → 512 with GELU and an intermediate LayerNorm.

How strong is this evidence?

The strongest result here is the direct latency measurement: after prefix caching, single-token constrained Qwen is close to CLM on these small and medium candidate sets. It refutes the assumption that choosing through an LLM necessarily requires a costly autoregressive generation loop. It does not prove that Qwen is universally as fast, particularly for huge action catalogs, dynamic candidate subsets, many concurrent requests or different hardware.

The weak point in the published comparison, for this question, is the missing same-backbone constrained baseline. A convincing broader study would match hardware, serving stack, precision, inputs and training budget; distinguish cold and warm caches; measure throughput and cache memory; and compare actual downstream success without a shield masking model errors.

Numerical validation: the CLM head port's maximum absolute difference against PyTorch was below 4×10⁻⁷ on checked normalized inputs. Six backbone embeddings compared against Transformers/PyTorch MPS had cosine similarity from 0.999890 to 0.999986. The duplicate-invoice CLM probabilities were 0.98797 with MLX and 0.98830 with Transformers. This substantially reduces the likelihood of a basic porting error, but is not an exhaustive vLLM equivalence test.
